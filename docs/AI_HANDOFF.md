## User Intent

The user wants to build SejaElevar as a browser-accessed platform for internal administrative work around apprentices/students, documents, document generation, course agendas/modules, companies, and progressively added tools.

The user wants the app UI in Brazilian Portuguese. Planning discussion may happen in English.

The project should prioritize practical functionality over fancy presentation at first: view data, search/filter it, edit it, and generate documents from that data plus values filled in through the web UI.

The first module is `Aprendizes`: list, search, filter, register/edit students, inspect related info, and eventually generate documents.

The intended model has three separate layers:

- The dev/meta repo: source code in `project/`, durable docs, staging assets, notes, Git, and AI memory.
- The baked/local app: a simple browser-accessed tool that can be passed to a coworker for testing/use. Current entry point is `SejaElevar.exe`, which starts the local provider and opens the browser UI.
- The data workspace: operational spreadsheets, templates, logos/assets, generated documents, and config, kept out of Git.

The first data workspace is pure local and populated by importing files into organized workspace folders. Later the same workspace model should be able to point at a Google Drive for desktop synced folder, Google Drive/Sheets APIs, or hosted storage. New alignment from June 13, 2026: the preferred future storage shape is one active base workbook, such as `Base SejaElevar.xlsx`, with worksheet tabs for `Aprendizes`, `Turmas`, `Arcos`, `Empresas`, `Aulas`, future `Cronograma`, and future `Presencas`, instead of separate active workbook files per entity.

## Current App

`project/` contains a Vite/React/TypeScript app shell with a light-blue sidebar, Elevar logo, app tabs for `Aprendizes`, `Documentos`, `Calendário`, `Turmas`, `Aulas`, `Arcos`, and `Empresas`, a search popup, settings popup, hide/show sidebar behavior, baked visual defaults, an `Aprendizes` XLSX import/table/edit/item-popup flow, and a linked `Turmas` flow that imports turma workbooks, groups turmas, and assigns/edits Aprendizes through their `Turma` field. `Aulas`, `Arcos`, `Documentos`, `Calendário`, and the other non-`Aprendizes`/`Turmas` tabs are placeholder pages for now. `Aprendizes` stays as a main tab for sorting, ordering, visualization, and current apprentice management until the Turmas flow truly replaces enough of that work. `Documentos` should become the central document hub for all students and institutional docs, templates, and generation actions; item popups may still expose contextual document links/buttons. `Calendário` should become the global/universal Cronograma visualization area. `Disciplinas` is not a main tab and should be managed inside Arcos because Arcos are directly composed of Disciplinas. `Salas` and `Funcionários` are also not main tabs at the moment and should be treated as future configurable/supporting linked values for Aulas/Cronograma unless the user reopens that decision.

The user should test with `project/dev/SejaElevar.exe`, not by opening `dist/` or raw generated files. The exe starts a local provider and opens the browser UI. The built dev package is intentionally tracked through Git/Git LFS for cross-PC handoff, while its live operational data inside `dados/`, `modelos/`, and `documentos_gerados/` remains ignored except `.gitkeep` placeholders. `exports/` is local generated output and is ignored by Git; recreate it from dev whenever the user requests a handoff package. The browser app intentionally renders nothing if opened directly without the exe/provider; do not add "open through the app" warning text to the UI.

Dev/release package rule: `project/dev/` and `exports/SejaElevar/` should have the same app shape and behave like the same app. The user tests the real flow in tracked `project/dev/` during normal development. Local-only `exports/SejaElevar/` is generated only when the user explicitly asks for release/export/package, by copying the already-tested dev executable/assets and applying release-only packaging changes. Dev may include explicitly dev-only live tuning controls; release hides/removes those, adds `README.md`, and starts with clean runtime data folders. Before generating release, bake the approved dev state into source and refresh/test dev so release does not differ unexpectedly.

Current provider lifecycle: the browser page sends heartbeats and a close signal. Closing the page/tab requests immediate provider shutdown; if the close signal is missed, the heartbeat timeout is the fallback. The provider should not be treated as a permanent background service. Current heartbeat interval is 1 second from the browser, and the provider fallback timeout defaults to 5 seconds.

Current `Aprendizes` behavior:

- If no `.xlsx` exists directly in `dados/`, the table stays in the import/missing-data state.
- Importing asks only for the source `.xlsx`.
- The provider copies the selected file directly into `dados/` and immediately names it `Aprendizes_hhmmssddmmyy.xlsx` using system time.
- Imported Aprendizes workbooks are validated against the current required columns in `project/src/shared/data/schemas.ts`. Blank cells are allowed and extra columns are preserved, but missing required column labels block import.
- `dados/controle.json` tracks the active Aprendizes workbook. Global recovery state now lives above individual workbook controls in `dados/controle-global.json` plus `dados/checkpoints/<checkpoint-id>/`. The root of `dados/` should contain only active on-use workbook files plus control/system files; old loose root `.xlsx` files are cleaned by the provider after import/save/patch/recovery, while historical recovery filesets live under `dados/checkpoints/`. The app does not treat manually dropped `.xlsx` files as active unless it must recover metadata from existing files.
- Important storage refactor direction: the current separate active Aprendizes/Turmas workbook files are an intermediate implementation. The planned cleaner user experience is one active app workbook with named worksheets. In that direction, `Importar` and `Exportar` become global buttons for the whole workbook, like `Recuperar Dados`, while pages read/write the worksheets they need.
- Aprendizes cell edits and column reordering write back to the active workbook. Real data changes save as a fresh timestamped on-use workbook, keeping one tracked backup workbook when available.
- Global checkpoints capture the whole app data state, currently active Aprendizes and Turmas workbooks together. The first app import creates a recoverable empty `before_import` checkpoint, so undoing the first import returns the app to the missing/import-needed state; redo restores the imported workbook through the normal reversible recovery path. Importing any workbook while app data already exists captures the previous whole-app state as a recoverable `before_import` checkpoint. The provider keeps up to three checkpoint filesets under `dados/checkpoints/`, newest first. Repeated sequential imports in the same launched app session amend the same import checkpoint/action and increment import metadata for plural recovery text; a new edit, recovery, or launched session breaks that sequence.
- `Recuperar Dados` opens a centered modal over a blurred/dimmed page. It lists available whole-app checkpoints with friendly labels in `HH:mm:ss dd/MM/yyyy` format. Confirming restores the chosen global checkpoint and stores the previous active whole-app state as the newest checkpoint, so recovery remains reversible and can itself be undone/redone.
- Current normal recovery descriptions identify: empty state before the first import(s), state before the last import(s), state before the last recovery, state before edits in the current session, or state before the last session with edits. The UI should avoid saying that recovery belongs to only Aprendizes, Turmas, or a single file; it is a `Dados` checkpoint.
- Cell undo is value-based: one completed cell edit is one undo entry, with a current global stack limit of 200. `Ctrl+Z` first reverts the active in-progress draft value, then walks backward through committed edits, registrations, deletions, imports, and recoveries; `Ctrl+Y` / `Ctrl+Shift+Z` redoes them. Undo/redo history is stored in browser storage so the dev app can continue the same action path across launched app sessions, as long as the referenced provider checkpoint filesets still exist. Undoing committed edits, registered rows, deleted rows, imports, and recoveries uses the same save/recover paths as normal data changes, so active workbooks and generated data indexes stay aligned.
- The top Aprendizes toolbar is grouped from right to left: dark/light mode, export/import/recover, delete/register/edit. `Exportar` copies the current active workbook to a user-chosen location using the same file name as the on-use workbook. The page title keeps a fixed font size, the toolbar buttons keep fixed 50px square sizing, and the toolbar is a bounded horizontal scroll lane beside the title once the buttons no longer fit.
- Column widths and row heights are visual app settings only and are not written to the spreadsheet.
- Header-click sorting is visual app state only and is not written to the spreadsheet. In normal view mode, clicking a column label cycles no sort -> ascending -> descending -> no sort. The active sort stays visible/applied while edit mode is toggled and while undo/redo navigates back to Aprendizes; data reload/save paths must preserve the latest live view settings rather than an old handler snapshot. Edit mode does not cycle sort by clicking headers. The sort indicator is a 2px line inside the active header: bottom edge for ascending and top edge for descending.
- The first visible table column is sticky/pinned horizontally so the row identity remains visible while scrolling sideways. The header uses a scrollbar spacer so header and body column dividers stay aligned at the far right.
- `Cadastrar Aprendiz` is now a popup-only registration mode in Aprendizes. There is no `cadastrar` draft row in the table. Toggling `Cadastrar` opens the item-style cadastrar popup; pressing the same toolbar button again, pressing the popup `X`, or selecting an existing row closes that mode. If an existing row popup is open, toggling `Cadastrar` swaps that popup into the cadastrar popup in the same placement instead of hiding it. The cadastrar popup mirrors the normal item popup fields and has a first bottom action button `Cadastrar Aluno` with a user-plus icon; it is disabled with the same inactive visual style as the top file buttons until any field has a value.
- While the cadastrar popup is open, pressing Enter in any editable field or clicking the enabled `Cadastrar Aluno` button appends the draft row to the end of the `.xlsx`, refreshes the generated data index through the normal save path, jumps the table to where the new row appears in the current visual order, highlights it briefly, clears the draft fields, and keeps the cadastrar popup open for the next registration. Registration edits are undo-aware before commit, and committed row insertions remain part of the normal undo/save/data-index path.
- Delete/register/edit actions are undo-aware. `Ctrl+Z` can focus the affected cell/row area when appropriate, but undo/redo should not open an item popup merely because a row changed; if a popup was already open, preserve or adjust it only as needed for row insert/delete. Undoing a deleted row restores it through the normal save path, and undoing a registered row removes it through the normal save path, so the workbook and generated data index stay aligned.
- The `Idade` column is treated as derived display data when `Data de Nascimento` is present. The app calculates and displays age from the plain-text birthdate, keeps `Idade` cells uneditable in the table, persists the derived age into the generated data index, and tries to preserve existing `Idade` workbook formulas when saving instead of overwriting the formula cells.
- The Aprendizes page stays mounted while switching tabs and gates the import state until the provider/workbook check finishes, so returning to Aprendizes should not briefly flash the import button before showing an already-loaded table.
- Importing a workbook whose headers do not match the current tool schema shows a bottom-right red toast for 3 seconds: `Arquivo escolhido não possui os valores necessários`. The toast is one line, floats above the app chrome/sidebar, and has a red bottom timer bar that drains right-to-left. Light mode uses a vivid red; dark mode uses a medium darker red.
- The main app content padding is fixed at 42px on the sides/bottom so resizing the window changes the available table area without shrinking the page margins or making the table drift.
- In normal Aprendizes view mode, clicking a row opens the current student/apprentice item popup and keeps that row highlighted. The popup closes only with its `X`; clicking another row swaps the selected item. It is anchored 20px from the table bottom/right when possible, then shrinks to stay inside the usable table area bounded by the sticky first column, header row, right edge, and bottom edge margins. Horizontal and vertical shrinking clips the details instead of resizing fields; the top details area can scroll with no visible scrollbar while the bottom action row stays visible. The popup currently shows editable fields for the Aprendizes values across seven fixed layers: Nome/Sexo/Data Nascimento/Idade, E-mail/Contato/CPF/RG, responsible contact info, Endereço, Empresa/Instituição Ensino, Arco/Função/Data Admissão/Data Término, and Turma. `Idade` remains read-only. Editable popup fields use the same edit/save/undo path as table cells. The bottom action area currently has a 60px square `Descadastrar` button with centered 32px icon and primary-color hover behavior. Settings/search popups must layer above item popups, and popup positioning is debounced during table/sidebar resizing so sidebar hide/show animation stays smooth while the popup is open.
- Current `Turmas` behavior is a linked-record flow. Import validates the required labels `Turma`, `Dia`, `Período`, `Instrutor`, `Sala`, `Disciplina`, `No. de Aprendizes`, and `Aprendizes`. The provider copies the selected workbook into `dados/` as `Turmas_hhmmssddmmyy.xlsx` and tracks the active Turmas workbook in `dados/turmas-controle.json`, with migration support for older local `dados/turmas.json` metadata. Turmas has provider endpoints for file serving, import/save/export, and provider-side value patching; recovery UI now uses the global `/api/recovery` endpoint instead of a per-Turmas backup meaning.
- The Turmas page stays mounted hidden, like Aprendizes, and loads both the active Turmas workbook and active Aprendizes workbook. Imported Turmas are shown as expandable groups. Each group can show assigned Aprendizes, using `Aprendizes.Turma` as the preferred source of truth. `+ Adicionar Aprendiz` opens a searchable picker of available Aprendizes, writes the chosen Turma value back to the Aprendizes workbook, syncs the derived `Aprendizes`/`No. de Aprendizes` values into the Turmas workbook, refreshes both generated data-index entities, and dispatches `sejaelevar:aprendizes-data-changed` so mounted pages reload from the updated source. The Turmas student details popup can edit Aprendizes fields from inside Turmas; its `Turma` field uses canonical dropdown matching against active Turmas names, and `Descadastrar Aprendiz` removes the selected Aprendiz row through the normal save/index path.
- Global undo now lives in `project/src/shared/undo/globalUndo.ts`. Aprendizes and Turmas register page controllers there, and `App.tsx` owns the app-level `Ctrl+Z`/redo capture/navigation. Undo entries are global rather than strictly page-local: if an action was made from another tab, undo/redo switches back to the origin tab and runs that page's handler so files, visible rows, item popups, and generated indexes stay aligned. Boundary undo helpers (`getGlobalUndoBoundarySnapshot`, `pushGlobalBoundaryUndoEntry`, and `replaceGlobalUndoStack`) support import checkpoints, while recovery is tracked as a normal reversible global action on top of the current history. `project/src/shared/data/events.ts` defines `GLOBAL_DATA_CHANGED_EVENT` so global import/recovery undo-redo can refresh mounted pages together and avoid stale hidden-tab state. The dev-only action history overlay lives in `project/src/shared/actionLog/`; it shows newest actions first, green for done, red for undone, yellow for undone actions whose redo path was discarded by a new action, and blue for explanatory cut/reason lines such as a 200-action limit cut or redo-path discard reason. Starting a new session does not add a blue line because undo/recovery history is intentionally preserved.
- The dev action-history log format should stay compact: `Tab | ação | item-ref | Valor: "antigo" -> "novo"`. Examples: `Aprendizes | editado | apr_xxxxx | Turma: "vazio" -> "Quarta Tarde"`, `Turmas | descadastrado | apr_xxxxx`, `Turmas | importado | Turmas_153022100626.xlsx`. Do not wrap the tab in brackets and do not use a long student name as the primary identifier. Current item refs should prefer the hidden stable app-managed record ID when available, with row-based refs only as a fallback.
- The dev-only action-history toggle is a sharp-corner square button with a history/rewind icon. When the log is open, the button sits outside the panel touching its right edge; wheeling over the button scrolls the log. This overlay is a development diagnostic and should remain removable without affecting product undo/data logic.
- Turmas value saving uses the provider endpoint `/api/turmas/values`. `project/launcher/Program.cs` handles the HTTP/workbook-control flow and delegates low-level workbook XML value patching to `project/launcher/WorkbookValuePatcher.cs`. This helper exists to keep fragile `.xlsx` internals isolated from the launcher. It patches workbook values in place as a best-effort attempt to preserve imported workbook structure; exact Google Sheets styling round-trips are not guaranteed and should not be chased with broad rewrites unless the user explicitly reopens that problem.
- The app now has a generated internal data index foundation. `project/src/shared/data/dataIndex.ts` builds normalized records from sheet rows, and the provider exposes `/api/data-index` plus `/api/data-index/entities/{entityId}`. `project/src/shared/data/stableIds.ts` manages a hidden workbook column `ID SejaElevar (não editar)`, excluded from public table/search fields, so generated records and future links can survive row moves, blank names, imports, and deletes. For Aprendizes, the UI rebuilds and persists `dados/sistema/data-index.json` after load/import/recover/save/edit/register/delete. For Turmas, the UI rebuilds and persists the `turmas` entity after load/import/recover/save and assignment changes; when Aprendizes data is available, `No. de Aprendizes` and `Aprendizes` are derived from linked Aprendizes, otherwise the count falls back to the comma-separated `Aprendizes` cell. Arcos, Disciplinas, and Aulas now have schema/index entity definitions ready for future import/tool implementation; Disciplinas stays internal/under Arcos in the UI rather than being a separate sidebar tab. The workbook remains the source of truth; the index is generated working memory for search, document generation, and future cross-tool variable lookups. The provider writes JSON as readable UTF-8, so PT-BR characters such as `ç`, `ã`, `é`, and `í` should be preserved in the file rather than escaped.
- `project/src/shared/data/baseWorkbook.ts` is the current code anchor for the future single-workbook model. It defines `Base SejaElevar.xlsx`, intended worksheet tabs, required columns, and which sheets still use legacy separate workbook endpoints. The provider exposes the matching read-only `GET /api/base-workbook/schema` endpoint. Current storage mode remains `multi-workbook-transition`; do not remove Aprendizes/Turmas endpoints until a real unified workbook adapter replaces them.
- Future linked fields should be treated as reference fields rather than plain text forever. `Turma` on an Aprendiz is now the first implemented dropdown sourced from active `Turmas`; `Empresa` on an Aprendiz should eventually follow the same pattern from registered `Empresas`. The `.xlsx` cells can stay human-readable by storing the canonical option name text; internally the app should normalize comparisons by ignoring accents/case/spacing so imported values like `Sao Jose` can match registered `São José`, then display/save/export the canonical name. If an imported value does not match a registered option, the app should preserve/show it but mark it as unregistered/invalid until the user resolves or registers it. This keeps source sheets plain while the generated index handles relationships for search, documents, and future pages like "aprendizes desta empresa/turma".
