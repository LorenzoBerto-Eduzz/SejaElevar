## User Intent

The user wants to build SejaElevar as a browser-accessed platform for internal administrative work around apprentices/students, documents, document generation, course agendas/modules, companies, and progressively added tools.

The user wants the app UI in Brazilian Portuguese. Planning discussion may happen in English.

The project should prioritize practical functionality over fancy presentation at first: view data, search/filter it, edit it, and generate documents from that data plus values filled in through the web UI.

The first module is `Aprendizes`: list, search, filter, register/edit students, inspect related info, and eventually generate documents.

The intended model has three separate layers:

- The dev/meta repo: source code in `project/`, durable docs, staging assets, notes, Git, and AI memory.
- The baked/local app: a simple browser-accessed tool that can be passed to a coworker for testing/use. Current entry point is `SejaElevar.exe`, which starts the local provider and opens the browser UI.
- The data workspace: operational spreadsheets, templates, logos/assets, generated documents, and config, kept out of Git.

The first data workspace is pure local and populated by importing files into organized workspace folders. Later the same workspace model should be able to point at a Google Drive for desktop synced folder, Google Drive/Sheets APIs, or hosted storage. New alignment from June 13, 2026: the preferred future storage shape is one active base workbook, such as `DadosElevar.xlsx`, with worksheet tabs for `Aprendizes`, `Turmas`, `Arcos`, `Empresas`, `Aulas`, future `Cronograma`, and future `Presencas`, instead of separate active workbook files per entity. Runtime timestamped copies should use `DadosElevar_hhmmssddmmyy.xlsx`.

## Current App

Page headers/top toolbars are no longer the main control surface: the visible page content now grows upward, while global app controls live in the sidebar bottom and collapsed-sidebar mini-bars. `Documentos`, `Empresas`, and remaining not-yet-built flows are placeholder-level for now. `Aprendizes` stays as a main tab for sorting, ordering, visualization, and current apprentice management until the Turmas flow truly replaces enough of that work. `Documentos` should become the central document hub for all students and institutional docs, templates, and generation actions; item popups may still expose contextual document links/buttons. `Calendário` is the global/universal Cronograma visualization/editing area. `Disciplinas` is not a main tab and should be managed inside Arcos because Arcos are directly composed of Disciplinas. `Salas` and `Funcionários` are also not main tabs at the moment and should be treated as future configurable/supporting linked values for Aulas/Cronograma unless the user reopens that decision.

Current `Calendário` behavior: the tab now has the global Cronograma week-view foundation, reading the same active `DadosElevar` availability as the other tabs. It renders a full-page Sunday-to-Saturday grid with 15-minute cells, 30-minute time labels, the same row/line/text sizing as the Turmas timetable, and an initial active-tab scroll to the `08:00` row. Its A1 cell uses the shared month/year picker popup. Selecting a month jumps to the week containing that month's first day. The Turmas timetable A1 uses the same shared month/year picker, while keeping its month-navigation arrows. `Calendário` renders and edits the same `Cronograma` event blocks as Turmas: events appear in their week/day/time positions, split cross-midnight events across days, horizontally lane overlapping events, and use the shared event-block UI for Aula/Turma/Instrutor/Sala, drag/resize/delete, and attendance hooks. Turmas remains a filtered view for one Turma; Calendário is the global view. On Calendário, sidebar collapse animation disables the expensive margin lerp so the large grid does not stutter during menu toggling.
